## Контекст

Наша команда из 4 человек разрабатывает учебное бизнес-приложение в рамках курса «Управление конфигурацией бизнес-приложений».

**Характеристики проекта:**

- Размер команды: 4 человека
- Длительность проекта: 16 недель (1 семестр)
- Частота релизов: промежуточные демо каждые 2 недели + финальный релиз
- Уровень опыта команды с Git: 2 человека уверенно, 2 — базово
- Требования к стабильности `main`: высокие, так как основная ветка должна содержать проверенную и готовую к демонстрации версию приложения

Для репозитория уже настроены защищённые ветки `main` и `develop`.

Прямые изменения защищённых веток запрещены. Изменения должны проходить через Pull Request минимум с одним approval.

**Проблема:** необходимо выбрать стратегию ветвления, которая позволит:

1. Параллельно работать нескольким участникам команды
2. Не допускать непроверенный код непосредственно в `main`
3. Иметь отдельную интеграционную ветку для совместной проверки изменений
4. Поддерживать отдельный процесс для обычных функций, исправлений и срочных hotfix
5. Соответствовать требованиям курса по Pull Request и Code Review

## Рассмотренные варианты

### Вариант A: GitFlow

**Суть:** GitFlow использует две долгоживущие ветки — `main` и `develop`. Новая функциональность создаётся в `feature/*`, исправления могут выполняться в `bugfix/*`, подготовка релизов — в `release/*`, а срочные исправления стабильной версии — в `hotfix/*`.

**Плюсы:**

- Чёткое разделение стабильной и интеграционной версий
- Несколько разработчиков могут независимо работать над разными задачами
- Есть отдельный процесс для релизов и срочных исправлений
- В `main` попадают уже интегрированные и проверенные изменения
- Подходит для работы через Pull Request и Code Review

**Минусы:**

- Сложнее GitHub Flow из-за большего количества типов веток
- Необходимо следить за актуальностью `develop` и `main`
- При долгоживущих feature-ветках повышается вероятность merge-конфликтов
- Для маленькой команды часть возможностей GitFlow может использоваться редко

**Подходит ли нам:** Да. Для нашей команды полезно разделение `main` и `develop`, поскольку позволяет сначала интегрировать и проверить изменения, а затем переносить стабильный результат в основную ветку.

### Вариант B: GitHub Flow

**Суть:** В GitHub Flow основная ветка `main` всегда должна быть стабильной. Для каждой задачи создаётся короткоживущая ветка, после чего изменение попадает в `main` через Pull Request.

**Плюсы:**

- Простая схема ветвления
- Небольшое количество долгоживущих веток
- Легко освоить новым участникам
- Хорошо сочетается с Pull Request и Code Review

**Минусы:**

- Нет отдельной интеграционной ветки `develop`
- Проверка совместной работы нескольких функций происходит ближе к `main`
- Требует особенно внимательно контролировать качество каждого PR
- Менее удобен, если команде нужен отдельный этап подготовки релиза

**Подходит ли нам:** С оговорками. Стратегия проще GitFlow, однако команда уже использует отдельную интеграционную ветку `develop`, поэтому GitHub Flow не соответствует выбранному процессу.

### Вариант C: Trunk-Based Development

**Суть:** Разработчики часто интегрируют небольшие изменения в одну основную ветку. Незавершённую функциональность при необходимости скрывают feature flags.

**Плюсы:**

- Частая интеграция уменьшает размер отдельных изменений
- Снижается риск очень больших merge-конфликтов
- Хорошо подходит для зрелого CI/CD
- Ускоряет получение обратной связи

**Минусы:**

- Требует развитых автоматических тестов и CI/CD
- Требует высокой дисциплины и частой интеграции
- Для незавершённых функций могут понадобиться feature flags
- Ошибка при недостаточных проверках быстро влияет на общую ветку

**Подходит ли нам:** Нет. На текущем этапе проекта полноценный CI/CD ещё не настроен, а защита веток и Code Review являются основными средствами контроля изменений.

## Решение

Мы выбрали стратегию **GitFlow**.

### Схема ветвления

```text
main        ●─────────────────●─────────────────●
             \               /                 / 
              \             /                 / 
hotfix         ●─────●─────●                 /
                                            /
release/*                           ●──────●
                                   /        \ 
                                  /          \ 
develop       ●──────●───────────●────────────●
               \      \         /
                \      \       /
feature/*        \      ●──●──●
                  \
feature/*          ●────────●
```

Основной поток новой функциональности:

```text
main
  ↑
  |
develop
  ↑
  |
feature/<название>
```

Рабочая ветка создаётся от `develop`.

После завершения задачи:

```text
feature/* → Pull Request → develop
```

После интеграции и подготовки стабильной версии изменения попадают:

```text
develop → Pull Request → main
```

Для срочного исправления стабильной версии используется:

```text
main → hotfix/* → main
```

После hotfix соответствующее исправление также должно быть перенесено в `develop`, чтобы ветки не расходились.

### Правила работы с ветками

1. `main` содержит только стабильную и проверенную версию приложения
2. `develop` является интеграционной веткой текущей разработки
3. Новая функциональность создаётся в `feature/<название>` от актуальной `develop`
4. Исправления в процессе разработки выполняются в `bugfix/<название>`
5. Подготовка релиза выполняется в `release/<версия>`
6. Срочное исправление стабильной версии выполняется в `hotfix/<название>`
7. Изменения в `main` и `develop` выполняются только через Pull Request
8. Для merge требуется минимум 1 approval от другого участника команды
9. Автор Pull Request не может одобрить собственный PR
10. После добавления новых коммитов предыдущий approval должен быть получен повторно
11. Все открытые обсуждения в PR должны быть закрыты до merge
12. Сообщения коммитов оформляются по Conventional Commits
13. После merge рабочая ветка удаляется

### Именование веток

Используются шаблоны:

```text
feature/<краткое-название>
bugfix/<краткое-название>
release/<версия>
hotfix/<краткое-название>
docs/<краткое-название>
```

Примеры:

```text
feature/version-endpoint
feature/ticket-status
bugfix/health-response
release/0.2.0
hotfix/startup-error
docs/contributing-rules
```

## Обоснование решения

### 1. Соответствие размеру команды

В команде 4 участника, поэтому несколько задач могут выполняться параллельно. GitFlow позволяет изолировать работу в отдельных feature-ветках и интегрировать её сначала в `develop`.

### 2. Стабильность основной ветки

Для проекта важно сохранять `main` в рабочем состоянии. Разделение `main` и `develop` уменьшает вероятность попадания в основную ветку изменений, которые ещё не прошли совместную интеграцию.

### 3. Code Review

В репозитории уже действует защита `main` и `develop`. Прямой push запрещён, для merge требуется Pull Request и минимум 1 approval.

GitFlow хорошо соответствует этой схеме: изменения проходят сначала через отдельную рабочую ветку, затем через review и только после этого попадают в защищённую ветку.

### 4. Подготовка релизов

Наличие `develop`, `release/*` и `hotfix/*` позволяет отделять обычную разработку от подготовки стабильной версии и срочных исправлений.

### 5. Требования курса

Выбранный процесс обеспечивает:

- работу через отдельные ветки;
- Pull Request для изменений защищённых веток;
- обязательный Code Review;
- минимум 1 approval;
- запрет прямого push;
- документированные правила работы команды.

## Последствия

### Положительные (+)

- `main` отделён от текущей разработки
- Есть отдельная интеграционная ветка `develop`
- У каждой задачи есть собственная рабочая ветка
- Удобно вести несколько задач параллельно
- Все изменения проходят через Pull Request
- Code Review является обязательной частью процесса
- Есть понятный процесс для release и hotfix
- История принятия изменений сохраняется в GitHub

### Отрицательные (-)

- В команде необходимо поддерживать сразу две долгоживущие ветки
- Процесс сложнее, чем GitHub Flow
- Неправильный выбор базовой ветки может привести к лишним конфликтам
- Долгоживущие feature-ветки могут сильно отстать от `develop`
- После hotfix необходимо следить, чтобы исправление присутствовало и в `develop`

## Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Feature-ветка сильно отстанет от `develop` и возникнут конфликты | Средняя | Среднее | Делить большие задачи на небольшие PR и регулярно синхронизировать рабочую ветку с `develop` |
| Непроверенный код попадёт в защищённую ветку | Низкая | Высокое | Использовать ruleset, обязательный Pull Request, минимум 1 approval и обязательное закрытие обсуждений |
| `main` и `develop` разойдутся после hotfix | Средняя | Высокое | После merge hotfix в `main` обязательно перенести исправление в `develop` отдельным PR |
| Участник создаст feature-ветку не от `develop` | Средняя | Среднее | Перед началом задачи выполнить `git checkout develop`, `git pull origin develop`, затем создавать рабочую ветку |
| Review будет задерживать merge | Средняя | Среднее | Первый ответ ревьюера должен быть дан в течение 24 часов; при недоступности ревьюера назначить другого участника |
